PainLab — App Map

A personal investigation system. Separates what you observed, what you suspect, what you tested, and what you learned.

The Investigation Loop

Pain → Observation → Hypothesis → Experiment → Result → Learning

Entry Type Visual System

Observation — sky/blue — something directly noticed or experienced
Hypothesis — amber — a possible explanation, not a fact
Experiment — violet — something tried to learn something
Result — emerald — what happened (not what it means)
Learning — rose — explicit interpretation, user-authored
Hard rule: recording a Result never changes a Hypothesis status or creates a Learning automatically. Both are deliberate user actions.

Screens

Home Screen
GET /
Lists all Pain Cases. Empty state explains the concept. Always shows "Start investigating a pain" action.
  • Case card: title, description, status badge, importance badge, entry count, tags
  • Create case modal: title (required), description (required), importance
  • On create → redirects to Case Detail
Case Detail Page
GET /cases/[id]
Two-column layout. Full investigation workspace.
  • Left: Current State panel — derived from entries, not AI-generated. Sections: The pain, Observed so far, Current hypotheses (with status), Active experiments, What I've learned, What remains uncertain (Proposed/Unresolved/Insufficient Evidence)
  • Right: Investigation Timeline — chronological, typed entries with distinct color borders + badges
  • Add to investigation — single action, type picker, opens per-type form
  • Edit — updates title, description, status, importance, tags

Entry Forms (via type picker on Case Detail)

Observation
  • Content (required) — "what did you observe?"
  • Observed at (datetime)
  • Context (optional)
Hypothesis
  • Statement (required) — "what do you suspect?"
  • Rationale (optional)
  • Status defaults to Proposed
  • Inline status edit: click badge in timeline → dropdown
Experiment
  • Title (required)
  • Question — "what are you trying to learn?" (required)
  • Procedure (optional)
  • Expected outcome (optional, recorded before running)
  • Start date (optional)
Result
  • Linked Experiment (required — enforced by UI + DB unique constraint)
  • "What happened?" (required, labeled factually not interpretively)
  • Outcome: As expected / Unexpected / Inconclusive
  • Unexpected effects (optional)
  • Disabled in picker until an Experiment exists
Learning
  • Statement (required) — "what did you learn?"
  • Basis (optional)
  • Confidence: Low / Medium / High
  • Never auto-generated

API Routes

POST /api/cases Create Pain Case
PATCH /api/cases/[id] Update Pain Case (title, description, status, importance, tags)
POST /api/observations Create Observation
POST /api/hypotheses Create Hypothesis
PATCH /api/hypotheses/[id]/status Update Hypothesis status only — never touches Results or Learnings
POST /api/experiments Create Experiment
POST /api/experiment-results Create Result (calls createExperimentResult only — hard rule)
POST /api/learnings Create Learning

Data Model (key relationships)

PainCase → has many: Observations, Hypotheses, Experiments, Learnings, Evidence*
Experiment → has one: ExperimentResult (@unique experimentId)
Experiment → optionally linked to one Hypothesis
HypothesisEvidenceLink* — join table (hypothesisId, evidenceId, SUPPORTS/CONTRADICTS)
* Evidence and HypothesisEvidenceLink exist in the schema, no UI in this slice

Architecture Boundaries

  • Service layer — only code that touches Prisma. No HTTP, no framework concerns.
  • API routes — validate with Zod, call one service function, return JSON. No business logic.
  • Components — server components fetch via service layer; client components call API routes.
  • AiProvider interface — defined at src/server/providers/ai/types.ts, NullAiProvider default. No calls in this slice.
  • ResearchProvider interface — defined at src/server/providers/research/types.ts. No calls in this slice.
  • currentSummary field — exists on PainCase, nullable, never written. Reserved for future AI narrative summary.
